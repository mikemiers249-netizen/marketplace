## Граница чеков по указанию владельца

Для стороннего селлера площадка принимает только свой сбор. Стоимость товара
остается к оплате селлеру при получении. В чеке площадки — одна агрегированная
строка «Услуга доступа к площадке» на сумму сборов, без наименований и стоимости
товаров сторонних продавцов. Товарные чеки остаются за селлерами.

Только магазин `ronnie83@mail.ru` принимает через площадку полную стоимость своих
позиций и передает полную товарную номенклатуру. Даже устаревшая индивидуальная
настройка `payment_mode=full_online` у другого селлера не меняет это правило.
В смешанной корзине один платеж и один чек состоят из собственных товарных позиций
этого магазина плюс услуги площадки по остальным; доставка не входит в сбор.

Новый расчет v2 сохраняет Receipt и привязку к позициям в `tariff_v2_fiscal_receipts`.
Это снимок при выставлении счета, не пересчет по каталогу после изменения цены или
названия. Возврат берет название и фискальные признаки из этого снимка: по селлеру
возвращается только услуга/сбор, по собственному магазину — его товар. Непредставимый
возврат по сохраненной цене единицы блокируется для сверки, а не меняет номенклатуру.
Эта новая ветка расчета пока не переключает рабочее оформление со скидками.

## Счета продавцам

`tariff_v2_bill_payments` сохраняет замороженную сумму, Receipt одной услуги,
платежный номер и случайный токен. Тестовая форма использует IsTest=1 и отдельные
ключи v2; прежний рабочий ResultURL и его настройки не меняются. Подтверждение
принимается общим тестовым callback v2 с подписанным Shp_flow=tariffs_v2_bill_test.
Возврат браузера не оплачивает счет.

Двойной запрос переиспользует активную попытку. Подписанная поздняя оплата
не игнорируется: оплачивает неизмененный счет, снимает долг и закрывает другие
неоплаченные формы этого счета. Если деньги пришли и по второй попытке, она
сохраняется как needs_review, не оплачивая долг второй раз. Чужой счет недоступен.
Пространство номеров v2 общее для storage/checkout/bill; обновление CHECK проверено
отдельно. PostgreSQL использует ALTER CONSTRAINT, локальная SQLite-копия —
контролируемое пересоздание таблицы с сохранением номеров и high-water sequence.
При активной проверке FK в старой SQLite команда не отключает ее самовольно.

## Постоянная очередь возвратов

`tariff_v2_refund_dispatch` хранит привязку к исходному платежу, сумму, чек,
идентификатор провайдера и этап queued/sending/submitted/finished/canceled/rejected/
unknown. Финансовое задание пока только ставит корректные заявки в очередь.

Обработчик проверяет исходную операцию, сумму и подписанные пользовательские
поля, затем сохраняет sending **до POST**. Успешное создание заявки означает
submitted, а не успешный возврат. Проверка состояния finished подтверждает возврат
и только затем разрешает включить комиссию в месячный счет. processing, ошибка
проверки, отмена и отказ не создают комиссионный долг.

Таймаут после POST или прерывание процесса оставляют неопределенный результат:
повторная отправка запрещена, нужна сверка. Ранний параллельный вызов не отправляет
второй POST. Очередь привязана к прежним реквизитам и номенклатуре, а не принимает
произвольный чек. В тестах работает только явно подставленный HTTP-транспорт;
тестовая оплата не может попасть в настоящий API возвратов.

Рабочий вызов API и автоматическое выполнение заданий **не включены**. API возвратов
еще не подключен пользователем; нужен Password3 в защищенных переменных Amvera.
Также остаются общий рабочий callback, production-профиль, планировщик и проверка
рабочей фискализации. Блокировки `tariffs-v2-release --check` сохранены.
