# Подготовка включения тарифов одной командой

**Рабочий выпуск пока не готов.** Эта инструкция и команда проверки не означают,
что можно включить всю систему на wimli.ru. Текущий код оплаты/удаления в основном
рассчитан на песочницу; отсутствующие рабочие интеграции перечислены ниже и в отчете
команды. Переменные окружения не обходят эти ограничения.

Цель: после завершения подготовки пользователь пишет «включи новые тарифы», а
единый сценарий выполняет проверки, миграции, настройку новых правил, переключение
и проверку результата. Сейчас подготовлены общий вход, аддитивная схема и протокол
возвратов. Само рабочее переключение еще не реализовано.

## Команды на сервере с подготовленным кодом

```sh
flask --app wsgi.py tariffs-v2-release --check
```

Команда доступна даже при `TARIFFS_V2_ENABLED=false`. Она читает состояние базы
и настройки, выводит JSON с `ready`, `blockers` и `activation_changed=false`.
Секреты и реквизиты подключения не выводятся. Ненулевой код выхода означает,
что выпуск заблокирован. HTTP-маршруты и задания этой командой не включаются.

```sh
flask --app wsgi.py tariffs-v2-release --prepare
```

Подготовить только дополнительные таблицы v2. В PostgreSQL изменения выполняются
в одной DDL-транзакции с advisory lock от параллельного запуска. Поддерживается
повторный запуск и прежняя локальная схема с отсутствующими `coverage.is_test`
или `storage_invoices.gateway_id`; прежние номера сохраняются. Последовательность
PostgreSQL после переноса номеров обновляется. При конфликте перенумерации нет.
Старые таблицы/тарифы/товары не переписываются; тестовая история не удаляется и
не становится рабочей. Это не полная миграция будущего production checkout.

Будущая единая команда рабочего выпуска:

```sh
flask --app wsgi.py tariffs-v2-release --activate
```

**Сейчас она обязательно откажет во включении.** Не следует снимать ограничения,
менять список блокировок или считать наличие таблиц признаком готовности.
Не подключены контроллер переключения и следующие рабочие части:

- [ ] Перевод рабочего каталога, корзины, заказов и кабинетов на v2 с сохранением
  доступа к старым заказам, переписке, модерации и существующим покупкам.
- [ ] Рабочая оплата с чеками, разделением тестовых/реальных данных и безопасным
  диапазоном InvId относительно старых платежей этого же магазина Robokassa.
- [ ] Постоянная очередь возвратов: отправка, ожидание, сверка неизвестного
  результата после таймаута, подтверждение провайдером и только затем долг продавца.
- [ ] Реальная оплата месячных счетов вместо локальной симуляции.
- [ ] Выдача электронной покупки из нового заказа в рабочую библиотеку.
- [ ] Исполнитель удаления рабочих карточек/файлов с повторной проверкой оплаты,
  сохранением финансовой истории и учетом изменения категории в момент сохранения.
- [ ] Планировщик с единственным исполнителем и защитой от дублей между workers.
- [ ] Контроллер включения/отката и проверка результата на HTTPS-стенде.
- [ ] Внешняя проверка платежей, чеков и возвратов на настроенном магазине.

## Настройки Robokassa

Пользователь сообщил: тестовые ключи оплаты уже хранятся в Amvera; API возвратов
еще не подключен. Ключи не нужно присылать в чат или сохранять в git.

Для оплаты в текущей изолированной системе используются отдельные переменные
`TARIFFS_V2_ROBOKASSA_TEST_LOGIN`, `TARIFFS_V2_ROBOKASSA_TEST_PASSWORD1`,
`TARIFFS_V2_ROBOKASSA_TEST_PASSWORD2` и `TARIFFS_V2_ROBOKASSA_HASH`.
Нельзя автоматически брать основной пароль при отсутствии тестового.
Текущие рабочие URL/ключи старой оплаты менять до подготовки общего обработчика нельзя.

Для рабочего режима зарезервированы защищенные переменные Amvera:

- `TARIFFS_V2_ROBOKASSA_LIVE_LOGIN`;
- `TARIFFS_V2_ROBOKASSA_LIVE_PASSWORD1`;
- `TARIFFS_V2_ROBOKASSA_LIVE_PASSWORD2`;
- `TARIFFS_V2_ROBOKASSA_PASSWORD3`;
- `TARIFFS_V2_REFUND_API_ENABLED` — после подключения API в кабинете Robokassa.

Наличие этих переменных само по себе не включает рабочие операции. Автоматический
возврат требует отдельного Password3. Идентификатор исходной операции проверяется
через OpStateExt: этот метод не работает для тестовых оплат. Поэтому тестовые
Password1/2 не доказывают готовность реального возврата. См. официальные
[API возвратов](https://docs.robokassa.ru/ru/refund-api) и
[XML-интерфейс](https://docs.robokassa.ru/ru/xml-interfaces).

Подготовленный клиент `app/utils/tariffs_v2_provider.py` проверяет исходную сумму
и назначение платежа, формирует подписанный JWT с составом чека и различает
создание заявки от завершенного возврата. При неоднозначном ответе создания
автоматического повторного POST нет: сначала потребуется сверка. Результат
`processing` не дает оснований включить сумму в счет продавцу. Клиент пока не
подключен к рабочим маршрутам или заданиям; текущие проверки используют вымышленные
ключи и подставной HTTP-транспорт, не реальные платежи.

## Что остается пользователю вне кода

Подключить API возвратов в кабинете Robokassa и сохранить Password3 в защищенных
переменных Amvera. Фискальные параметры должны соответствовать настройкам магазина;
не следует выбирать их по умолчанию в коде без проверки. Изменения на сервере,
выкладка и рабочее переключение в рамках этого этапа не выполнялись.

Проверки: основной прогон 205 тестов (204 успешно, один пропущен из-за ограничения
Windows на символьную ссылку); отдельно все 8 PostgreSQL-проверок успешны.
Последняя проверка PostgreSQL включает повторную подготовку старой промежуточной
схемы, сохранение номера счета и продвижение последовательности без повторного InvId.
