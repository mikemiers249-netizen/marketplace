# Оплата заказов через Robokassa

Интеграция выключена по умолчанию. Приём оплаты разрешён только для продавца,
чей email задан в `ROBOKASSA_SELLER_EMAIL`. Другие продавцы не попадают в этот
магазин Robokassa. Корзина с несколькими продавцами оплачивается отдельными
счетами, без смешивания получателей.

## Настройки окружения Amvera → MP

```dotenv
ROBOKASSA_ENABLED=True
ROBOKASSA_MERCHANT_LOGIN=wimliru
ROBOKASSA_SELLER_EMAIL=<email выбранного продавца>
ROBOKASSA_HASH_ALGORITHM=md5
ROBOKASSA_TEST_MODE=True
ROBOKASSA_TEST_PASSWORD1=<тестовый пароль 1>
ROBOKASSA_TEST_PASSWORD2=<тестовый пароль 2>
ROBOKASSA_PASSWORD1=<рабочий пароль 1>
ROBOKASSA_PASSWORD2=<рабочий пароль 2>
```

Пароли задаются исключительно в секретных переменных окружения. Не коммитить
их и не отправлять в журналы. Тестовые и рабочие пароли должны различаться.
Хеширование в Robokassa должно совпадать с переменной окружения (по умолчанию MD5).
Поддерживаются также SHA256 и SHA512; для тестового режима задаётся тот же алгоритм.
Пароль 3 не используется.

В технических настройках магазина:

| Поле | Значение | Метод |
| --- | --- | --- |
| Result URL | `https://wimli.ru/payments/robokassa/result` | POST |
| Success URL | `https://wimli.ru/payments/robokassa/success` | GET |
| Fail URL | `https://wimli.ru/payments/robokassa/fail` | GET |

## Проверка и запуск

1. Развернуть код. `flask db-init` создаёт новую таблицу `robokassa_payments`;
   схема существующих заказов не меняется. Миграция `b14c36d8e205` также создаёт
   эту таблицу идемпотентно. Не удалять таблицу: её ID используются как InvId.
2. Настроить URL и тестовые пароли. Оформить отдельный тестовый заказ выбранного
   продавца и пройти Robokassa. Подтверждение пишет тестовый счёт как `paid`,
   но реальный заказ остаётся неоплаченным.
3. Проверить в БД/журнале, что ResultURL принят и возвращает `OK<InvId>`.
4. После успешной проверки добавить рабочие пароли и переключить
   `ROBOKASSA_TEST_MODE=False`. Приложение необходимо перезапустить.
5. Выполнить согласованную реальную контрольную оплату; покупатель сам вводит
   платёжные данные и подтверждает списание. Проверить заказ и операцию в Robokassa.

Встроенные тесты: `python -m unittest discover -s tests -p test_robokassa.py -q`.

## Подтверждение и исключения

Сумма фиксируется в БД на старте оплаты и считается через `grand_total`
(товары + доставка − бонусы − промокод). Запрос из браузера не может задать сумму.
Возвраты SuccessURL/FailURL не меняют статусы. Только ResultURL с верной подписью
паролем 2 и точной суммой подтверждает оплату в `robokassa_payments`.
`Order.payment_confirmed` показывает оплату отдельно от статуса обработки/доставки,
чтобы оплаченный заказ продолжал собираться и отправляться обычным способом. Повторные уведомления
идемпотентны. Для одного заказа допускается один счёт в каждом режиме.

После оформления через `/order-review/submit` заказ выбранного продавца
перенаправляется на `/payment?order_id=...`; кнопок оплаты в списке заказов нет.
Завершённый тест отмечается отдельно и не предлагается к повторной оплате.

Оплата отменённого заказа либо заказа с изменившейся суммой сохраняется как
`needs_review`, не восстанавливая заказ. В журнале появляется запись с ID счёта
и заказа; такой платёж требует ручной проверки и, при необходимости, возврата
через Robokassa. Автоматического возврата и интерфейса сверки в этой версии нет.

Рабочие подписи и суммы не заменяют проверку номенклатуры, налогового режима и
настроек чеков в аккаунте Robokassa. Текущая интеграция рассчитана на выбранный
магазин самозанятого; для других получателей и схемы маркетплейса нужна отдельная
интеграция. Параметр Receipt для касс ИП/ООО здесь не формируется.
